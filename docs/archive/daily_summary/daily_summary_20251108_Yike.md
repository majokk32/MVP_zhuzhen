### 提交逻辑核心修复

#### 删除旧提交记录逻辑优化
- **问题诊断**: 发现删除旧提交时只删除了数据库记录，但对应的文件夹没有被删除，导致文件系统中有遗留文件夹
- **根本原因**: 
  - 时区不匹配：数据库中的`created_at`是UTC时间，而文件夹名使用的是北京时间（UTC+8）
  - 删除逻辑只根据数据库记录匹配文件夹，时区转换不正确导致匹配失败
- **解决方案**:
  - 修复时区转换：添加`utc_to_beijing()`函数，将UTC时间正确转换为北京时间
  - 双重保障机制：
    1. 方法1：根据数据库记录删除对应文件夹（使用正确的时区转换）
    2. 方法2：扫描文件夹，删除所有不在保留列表中的遗留文件夹（清理历史遗留）
  - 从保留记录的`images` URL中提取文件夹名，确保准确匹配
- **修复效果**: 
  - 成功删除旧提交的数据库记录和对应文件夹
  - 自动清理历史遗留文件夹（即使数据库记录已不存在）
  - 确保每个任务每个学生只有一个提交文件夹

#### 时区统一为北京时间
- **问题**: 代码中混用UTC时间和本地时间，导致时间匹配和显示不一致
- **解决方案**:
  - 创建统一的时区工具函数：`get_beijing_time()`和`utc_to_beijing()`
  - 所有时间创建统一使用北京时间（UTC+8）
  - 修复文件：
    - `app/api/submissions.py`: 添加时区工具函数，修复`graded_at`和`cutoff_time`
    - `app/utils/storage_new.py`: 文件夹创建时间使用北京时间
    - `app/utils/file_decoder.py`: 文件夹创建时间使用北京时间
- **修复效果**: 所有时间相关操作统一使用北京时间，确保一致性

#### 前端提交次数显示修复
- **问题**: 前端使用`submissions.length`计算提交次数，由于旧记录被删除，始终显示为1次

- **解决方案**: 
  - 前端改为使用`submission.submit_count`字段显示提交次数
  - 后端API已返回`submit_count`字段（`SubmissionInfo` schema包含该字段）
- **修复效果**: 前端正确显示实际提交次数（如2/3次），与数据库一致

### 复盘逻辑核心修复

#### 复盘完成HTTP 500错误修复
- **问题**: 点击"完成复盘"时出现HTTP 500错误：`Multiple rows were found when one or none was required`
- **根本原因**: 
  - 查询条件返回了多条PENDING状态的记录（如review_count=1和review_count=2都是PENDING）
  - 使用`scalar_one_or_none()`期望0或1条记录，但实际返回了多条
- **解决方案**:
  - 在查询中添加`.limit(1)`限制只返回1条记录
  - 使用`order_by(EbbinghausReviewRecord.review_count)`确保选择最早的复盘（review_count最小的）
- **修复效果**: 复盘完成功能正常工作，不再出现500错误

#### 复盘记录ID标识修复
- **问题**: 后端返回的`id`使用了`submission_id`，导致同一个submission的多个复盘任务共享同一个ID
- **根本原因**: 
  - 同一个submission可能有多个review records（不同次数的复盘：review_count 0, 1, 2, 3...）
  - 使用`submission_id`作为ID会导致多个任务无法区分
- **解决方案**:
  - 后端修复：将返回的`id`改为`record.id`（review record的主键）
  - 同时添加`review_record_id`字段明确标识
  - 后端更新逻辑：优先使用`review_record_id`精确查找，回退到`submission_id`查找（保持兼容性）
  - 前端修复：在更新API调用中添加`review_record_id: currentTask.id`
- **修复效果**: 
  - 每个复盘任务都有唯一的ID
  - 点击一个任务的"复盘"按钮时，只有该任务会被更新
  - 其他任务的状态保持不变

#### 复盘任务提前创建逻辑说明
- **现象**: 完成review_count=1的复盘时，系统创建了review_count=3的记录（scheduled_date=2025-11-15）
- **原因分析**: 
  - 这是预期行为：完成当前复盘时，提前创建下一个复盘记录
  - 前端查询条件：`scheduled_date <= today`，只显示今天或已过期的任务
  - 未来的任务（如15号的）不会显示，但已创建，等日期到达时自动显示
- **结论**: 这是为未来日期做准备的设计，属于正常逻辑

### 较小的逻辑修复

#### 复盘查询去重逻辑
- **问题**: 可能存在重复的复盘记录（相同的submission_id和review_count）

- **修复效果**: 前端不会显示重复的复盘任务
